# Inside the CPU: Storage and Disk Lab

Runnable code from the [Inside the CPU: Storage and Disk Lab](https://www.youtube.com/@TomJNet) video series: blocks and sectors, filesystems, the read and write system calls, the page cache, SSD and NVMe internals, direct I/O and storage benchmarks.
One folder per episode, one complete C++20 program per idea shown on the slides, and next to each one its C17 twin (`NN_name.c` beside `NN_name.cpp`) that teaches the same idea in plain C, plus the shell scripts that run the Linux tools of the episode.

| Computer Storage in 5 Minutes: HDD, SSD and NVMe | The first episode of the Storage and Disk Lab of the Inside the CPU series, in five minutes. Why storage exists at all (RAM forgets at power off), how a hard disk pays about 10 ms for every seek, why a SATA SSD with NAND flash answers in about 100 microseconds, and why an NVMe drive with the same flash is faster still: it sits on PCIe and replaces the single AHCI queue of 32 commands with up to 64K queues, usually one pair per CPU core. Everything lands on one latency ladder, from the L1 cache at about 1 ns to a disk seek at about 10 ms. In the lab, lsblk tells you which devices your Linux machine has, and a small C++ program rescales the typical latencies so that an L1 hit takes one second. The numbers are typical orders of magnitude, not measurements: run the samples and read your own machine. | `01-storage-lab-hdd-ssd-nvme-in-5-minutes` |

In ten minutes we see what each unit is, why they usually line up at 4 KiB, how a logical block address (LBA) names a sector, why a partition is only a range of LBAs, and why a write that ignores the boundaries costs twice the device work. In the lab we build a tiny filesystem in C++ (inode table, directory map, block bitmap) that creates files and prints which blocks they got, resolve a path hop by hop, make hard links with std::filesystem, and check the real filesystem with stat, ls -i, df -i and filefrag. We follow that call across the line: the syscall instruction, the mode switch from ring 3 to ring 0, the checks, the copy from your buffer into the page cache, and the return value, which may be smaller than what you asked for. In the lab we write 1 MiB three ways (one byte per write call, one call for the whole buffer, one byte per put through std::ofstream), read the ratio on our own machine, count the calls with strace, and finish with the difference between flush and fsync. We cover what a hit and a miss typically cost, read ahead, the writeback limits (30 seconds, 10 percent and 20 percent of memory), what fsync and fdatasync force, why mmap is a window into the same pages, and when the cache gets in the way. A NAND cell stores charge, cells form pages of about 4 to 16 KiB that are the unit of read and program, and pages form erase blocks of megabytes that are the unit of erase. Flash cannot overwrite in place, so the flash translation layer (FTL) in the controller maps every LBA to the physical page that holds its latest copy and leaves stale pages behind. From there come garbage collection, write amplification, over provisioning, wear leveling and TRIM. The lab builds a small FTL model in C++20: overwrite the same LBA again and again, print the mapping, trigger garbage collection and print the write amplification factor. We open a file with O_DIRECT in C++ and handle the filesystems that refuse it, align the buffer, the offset and the length to 4096 bytes, time a buffered write, a write plus fsync and a direct write, watch Dirty in /proc/meminfo, build the cache that the application now has to bring itself, and model the two shared rings of io_uring. The honest result: direct I/O is not faster than RAM, it is more predictable. The three paths, the alignment rules and the io_uring rings are animated. All latencies are typical orders of magnitude, not measurements: run the samples on real Linux hardware and read your own. | `08-storage-lab-buffered-vs-direct-io-in-10-minutes` |

IOPS, throughput and latency are three views of the same stream of requests, and two formulas tie them together: throughput equals IOPS times block size, and the requests in flight equal IOPS times latency (Little's law). We raise the queue depth on a model SSD until the knee where IOPS go flat and latency climbs, compare sequential and random, read and write, HDD and NVMe, and replace the average with p50, p99 and p99.9. Then the lab: why a benchmark must bypass the page cache, why an SSD must reach its steady state, three fio jobs and how to read the fio report, and a short C++ program that does 4 KiB random reads with pread, buffered and with O_DIRECT, and prints its own percentiles. ## The lab

- C++20 with `g++` on Ubuntu 24.04, x86 64 hardware. WSL Ubuntu is fine for writing and running most samples.
- Take timings on real Linux hardware: a virtual machine shares cores and hides the counters `perf` reads, and WSL shows no real PCIe devices, IRQs or NUMA nodes.
- Linux system calls sit inside `#if defined(__linux__)`. On Windows the programs still build and run, and print what the Linux branch would show.
- Every timing program prints its own numbers for the machine it runs on and never fails because of them. A call the system refuses (no root, one NUMA node, a filesystem without direct I/O) prints why and moves on.
- Hardware a program cannot touch is a small C++ model with deterministic output: read it, run it, change it.

## Build and run

Ubuntu or WSL Ubuntu:

```bash
sudo apt update
sudo apt install build-essential make linux-tools-common linux-tools-generic
```

Every folder has the same Makefile, for both languages. It picks the compilers by operating system: MSVC on Windows (run from a Developer Command Prompt), g++ and gcc on Linux, clang++ and clang on macOS.

```bash
cd 04-storage-lab-read-write-system-calls-in-10-minutes
make STD=c++20          # build everything
make run STD=c++20      # build and run every sample
make cpp STD=c++20      # only the C++ samples
make c                  # only the C samples (C17; make CSTD=c11 to change)
make run-NN_name_c      # one C sample: NN_name.c builds NN_name_c
make clean
```

The C samples build with `gcc -std=c17 -Wall -Wextra -pedantic -O2 -pthread` on Linux and MinGW, and with `cl /std:c17 /experimental:c11atomics /W4` on Windows. They use C11 `<threads.h>` and `<stdatomic.h>`; MinGW has no `<threads.h>`, so the files that start threads carry a ten line mapping onto pthreads.

The `.sh` scripts need Linux; some commands in them need `sudo` or real hardware and say so.
